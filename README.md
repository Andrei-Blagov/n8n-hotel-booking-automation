# n8n Hotel Booking Automation

Демонстрационный проект автоматизации бронирования отеля на **n8n** с использованием **Google Sheets** и **Gmail**.

Проект показывает не просто линейный workflow, а полный бизнес-сценарий: приём заявки, валидацию, поиск доступного номера с учётом пересечения дат, создание брони, обработку отказа, email-уведомления и ежедневный управленческий отчёт.

## Что внутри

- `workflows/01-new-booking-request.json` — обработка новой заявки.
- `workflows/02-daily-report.json` — ежедневный отчёт по бронированиям.
- `sample-data/rooms.csv` — пример справочника номеров.
- `sample-data/bookings.csv` — пример структуры бронирований.
- `docs/architecture.md` — архитектура и бизнес-логика.
- `docs/setup.md` — краткая инструкция по запуску.

## Сценарий новой заявки

```text
n8n Form
  ↓
Validation
  ├─ error → Save validation error → Gmail alert to manager
  ↓
Read Rooms + Read Bookings
  ↓
Wait for both datasets
  ↓
Find available room
  ├─ not found → Save request → Gmail "No room available"
  ↓
Create booking
  ↓
Gmail confirmation
```

### Логика доступности

Номер не переводится глобально в `reserved`. Доступность рассчитывается по существующим бронированиям и их датам.

Два периода считаются пересекающимися, если:

```text
requested_start < existing_end
AND
requested_end > existing_start
```

Поэтому один и тот же номер может быть забронирован повторно после даты выезда предыдущего гостя.

Например:

```text
13–16 сентября → R-101 занят
14–15 сентября → R-101 недоступен
16–18 сентября → R-101 снова доступен
```

Если на нужные даты занят первый подходящий номер, workflow проверяет следующие номера того же отеля и типа.

## Ежедневный отчёт

Второй workflow запускается по расписанию и формирует HTML-отчёт:

- новые бронирования за день;
- брони, ожидающие оплаты;
- фактическая загрузка номерного фонда на дату отчёта;
- количество свободных номеров;
- проблемные заявки (`not_available`, `error`).

Отчёт отправляется менеджеру через Gmail.

## Проверенные сценарии

Проект протестирован на следующих случаях:

1. Свободный номер → создаётся бронь и отправляется подтверждение.
2. Первый номер занят на эти даты → выбирается второй подходящий номер.
3. Все подходящие номера заняты → заявка получает `not_available`.
4. После даты выезда тот же номер снова становится доступен.
5. Ежедневный отчёт корректно различает будущие брони и фактическую занятость на текущую дату.

## Google Sheets

Используются два листа.

### `Rooms`

Минимально необходимые поля:

```text
room_id
hotel_name
room_type
price
```

В демонстрационной структуре также могут присутствовать `date_from`, `date_to`, `status`. Они не используются как глобальный признак занятости: занятость определяется по листу `Bookings`.

### `Bookings`

```text
booking_id
client_name
email
hotel_name
room_type
date_from
date_to
room_id
price_per_night
nights
total_price
status
payment_status
created_at
```

## Безопасность публичного workflow

Публичные JSON обезличены:

- удалены OAuth credential references;
- удалены webhook IDs;
- удалён ID исходной Google-таблицы;
- удалены instance-specific IDs;
- персональный email менеджера заменён на `manager@example.com`.

После импорта необходимо подключить собственные Google Sheets и Gmail credentials.

## Ограничение демо-архитектуры

Google Sheets подходит для демонстрации и небольшого потока заявок. При высокой конкурентной нагрузке проверка доступности и создание брони должны выполняться транзакционно в базе данных, чтобы исключить одновременное бронирование одного номера двумя запросами.
